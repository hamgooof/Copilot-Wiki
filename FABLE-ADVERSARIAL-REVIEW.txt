================================================================================
1. EXECUTIVE VERDICT
================================================================================

READY WITH CORRECTIONS.

The wiki is structurally sound for Azure DevOps publication, the learning path is
genuinely progressive, and the large majority of factual claims — including every
billing, CLI-compaction, skills-location, Memory, Spaces, content-exclusion and
subagent-model-precedence claim I checked — are supported verbatim by the cited
primary documentation. The hedging discipline ("current CLI documentation says…",
To Test labels) is unusually good and repeatedly saved pages from findings.
However, one publishing instruction on the maintenance page is wrong in a way that
would expose non-wiki internal files if followed (ADV-01), the GH-600 page misquotes
three of six exam domain names from the live study guide (ADV-02), and two clusters
of VS Code claims are attributed to pages that do not contain them (ADV-03, ADV-04).
Fix ADV-01 and ADV-02 before publishing; the rest are correction-pass items.

ADV-01  P0  Publishing instruction is wrong and would expose internal files
--------------------------------------------------------------------------------
File: Sources-and-Maintenance.md, line 87
What is wrong: "Publish the repository root (`/`) so `Confluence/` is the wiki
root." This is self-contradictory: in Azure DevOps you "select the repo, branch,
and folder that contain the Markdown files", and "If you want to publish all
Markdown files in the repo to your wiki, select the root of the repo (/) as the
folder" (Microsoft docs). Publishing the root makes the REPOSITORY root the wiki
root: Confluence becomes a subpage, the root .order inside Confluence/ no longer
selects the wiki home page, and every other .md in the repository is published.
The parent directory currently contains dozens of internal working files
(CLAUDE.md, HANDOVER-*.md, OVERNIGHT-*.md, benchmark reports, review prompts) that
would become wiki pages visible to all readers.
Why it matters: following the wiki's own documented publish procedure breaks the
intended hierarchy AND leaks internal material — a materially unsafe publication.
Source: https://learn.microsoft.com/en-us/azure/devops/project/wiki/publish-repo-to-wiki?view=azure-devops
("In the Publish code as wiki dialog, select the repo, branch, and folder that
contain the Markdown files.")
Correction: change the sentence to "Publish the `/Confluence` folder (not the
repository root) so `Confluence/` is the wiki root." One-line fix.

ADV-03  P2  AGENTS.md "nearest file takes precedence" attributed to VS Code docs
            that do not say it
--------------------------------------------------------------------------------
File: CopilotTechnologies/Custom-instructions.md, line 82
What is wrong: "VS Code documentation describes the nearest `AGENTS.md` in the
directory tree as taking precedence." The current VS Code custom-instructions
page says VS Code "automatically detects an AGENTS.md Markdown file in the root
of your workspace", and — behind an experimental setting — "searches recursively
in all subfolders of your workspace for AGENTS.md files and adds their relative
path to the chat context". No nearest-wins precedence rule is stated anywhere I
could find on code.visualstudio.com. Additionally, the page's own Sources list
contains no VS Code link, so the attribution cannot be checked from the page.
Why it matters: a reader designing a monorepo layout around nearest-file
precedence would be building on an undocumented rule — exactly the failure mode
the surrounding paragraph warns against.
Source: https://code.visualstudio.com/docs/agent-customization/custom-instructions
Correction: replace the bullet with what the doc actually says (root-level
AGENTS.md applied to all requests; experimental subfolder discovery), add the
VS Code source link, and map the open question to test T02.

ADV-05  P2  Glossary "Checkpoint" definition collides with VS Code's checkpoint
            feature
--------------------------------------------------------------------------------
File: Copilot-Terminology.md, line 37
What is wrong: "Checkpoint | A saved record associated with context compaction on
supporting surfaces, such as current Copilot CLI." Correct for the CLI ("A
checkpoint is a saved copy of the compaction summary…" — CLI context-management
docs). But VS Code — the surface most readers use — uses the same word for
session rollback: "checkpoints let you roll back a session" (VS Code
trust-and-safety page, which this wiki cites elsewhere). A VS Code user reading
this glossary will misinterpret the checkpoints they actually see in the UI.
Why it matters: the glossary exists precisely to disambiguate overloaded terms;
this entry creates the ambiguity it should resolve.
Sources: https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agents/copilot-cli/context-management ;
https://code.visualstudio.com/docs/agents/concepts/trust-and-safety
Correction: split the entry: "In Copilot CLI, a saved copy of the compaction
summary. In VS Code, a restore point for rolling back a session's file changes.
Different mechanisms sharing one name."

ADV-10  P3  "CopilotTechnologies" renders without spaces in navigation
--------------------------------------------------------------------------------
Files: CopilotTechnologies.md / CopilotTechnologies/ (names)
What is wrong: Azure DevOps derives page titles from filenames, with hyphens
rendered as spaces ("In the file name, a hyphen (-) represents a space in the
page title" — Microsoft docs). Every other page will display with spaces
("How Copilot Works"); this node will display as "CopilotTechnologies".
Why it matters: cosmetic inconsistency on the wiki's main section node; renaming
after publication breaks bookmarks, so decide before first publish.
Source: https://learn.microsoft.com/en-us/azure/devops/project/wiki/wiki-file-structure?view=azure-devops
Correction: rename to Copilot-Technologies.md + Copilot-Technologies/ and update
both .order files and all relative links — or accept the rendering and note it.

================================================================================
5. AUDIENCE AND LEARNING-PATH ASSESSMENT
================================================================================

Appropriately progressive: the root sequence (how it works → terminology →
tokens/context → turns/tools/loop → efficiency) builds each concept before use;
the glossary genuinely precedes the first heavy use of "subagent", "MCP" and
"compaction"; every technology page opens with a plain-English one-liner and a
"read this first" pointer; the Choose-the-right-technology decision list and the
skill-vs-agent worked examples are exactly the comparisons the brief asked for;
the wiki consistently says when the simpler interaction is enough ("Do not use
full agent autonomy for every small edit"; "Avoid a custom agent when the only
requirement is some guidance text").

Where a regular user may still get lost:
- Cache Explorer and the VS Code context indicator are named without any access
  path (ADV-04, ADV-07) — the two places the wiki says "go observe it" are the
  two places the reader can't follow.
- "Checkpoint" will actively mislead VS Code users (ADV-05).
- Choose-the-right-technology uses "hook" and "plugin" in the decision list one
  page before Other-useful-technologies explains them; the glossary mitigates
  this, but a "see Other useful technologies" pointer on first use would help.
- The wiki distinguishes surfaces constantly (correctly) but never enumerates
  them; see opportunity 1.

No page reads as platform-engineer-only; To-Test.md is explicitly labelled for
experimenters and does not masquerade as user guidance.
