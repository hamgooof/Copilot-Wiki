# Tokens and context windows

_For new and regular Copilot users - Last reviewed 4 October 2026_

Models read and write in tokens, which are chunks of text. One token is about four characters of English. The context window is how many tokens fit in one model call: everything sent in, plus room for the reply and any reasoning. When it fills up, quality and cost both suffer.

[[_TOC_]]

## The whiteboard analogy

Imagine the model working at a whiteboard of a fixed size:

- Pieces of text are converted into numbered **tokens**, like numbered magnetic tiles
- The **model input** is everything placed on the board for one model call: instructions, the conversation so far, file contents and tool results
- The **context window** is the whole board, including space reserved for the answer and any supported reasoning
- The board is all the model can see. Anything not on it, including earlier sessions, does not exist for this call
- **Compaction** replaces some older detail with a shorter summary
- A **new session** starts with a clean board

A bigger board does not help if it is covered in things the task does not need.

## What a token is

A **tokeniser** splits text into pieces (a word, part of a word, or punctuation) and gives each a number, the **token ID**. The model works on those numbers, not on letters.

![One tokeniser turning pieces of text into numeric token IDs](Media/tokenisation-example.svg =720x)

Each model has its own tokeniser, so the same text gives different counts on different models. You never need to count tokens yourself.

## Token counts in more detail

| Count | What it represents |
| --- | --- |
| **Input** | Instructions, tool definitions, messages, supplied file content and earlier tool results sent for a model call |
| **Output** | Text and tool requests generated by the model |
| **Cached input** | A matching input prefix the provider can reuse from an earlier call |
| **Reasoning** | Thinking text some models generate before answering |

## How context grows during a turn

A **turn** runs from your message to Copilot's final response. A **round** is one pass through the model-and-tools loop.

This simplified picture of the checkout task in [One turn, many rounds](One-Turn-Many-Rounds.md) uses four equal blocks; real rounds vary in size.

![Four simplified stages showing model input growing during the checkout-test turn, followed by compaction](Media/context-growth-across-rounds.svg =780x)

Each round adds a block and resends all the earlier ones, so four rounds process `1 + 2 + 3 + 4 = 10` blocks, not 4. Twice the rounds is roughly four times the input. The hatched blocks were sent before; if the provider still has them cached, they are charged at the cheaper cached rate. Real rounds vary in size, so treat this as a picture of growth, not a price.

## What happens when the window fills

Before the window runs out, VS Code [summarises older parts of the conversation](https://code.visualstudio.com/docs/agents/concepts/context#_context-window-and-compaction) to free space. You can also do this yourself with **Compact Conversation**. Summaries lose detail: an exact command, a decision, an edge case.

If something must survive, write it in a file in the repository, where Copilot can read it again.

## Inspect context and usage

VS Code shows how full the context window is.

![Illustrative context-window indicator showing used, reserved and free capacity](Media/context-indicator.svg =560x)

In VS Code agent sessions, select the context indicator in Chat to inspect the session and compact it. VS Code also has Agent Debug Logs and [Cache Explorer](https://code.visualstudio.com/docs/agents/agent-troubleshooting/cache-explorer) if you want to look deeper.

## Common sources of context bloat

- Long instruction files full of rarely relevant workflows
- Several files repeating the same rules
- Attaching a whole folder when a small set of files would do
- Reusing one session for unrelated tasks
- Commands that return large amounts of irrelevant output
