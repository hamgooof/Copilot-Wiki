# Tokens and context windows

_For new and regular Copilot users - Last reviewed 12 August 2026_

Tokens are the units a model processes. The context window is the limited working capacity shared by the model's input, generated output and any supported reasoning.

[[_TOC_]]

## The whiteboard analogy

Imagine the model working at a whiteboard of a fixed size:

- Pieces of text are converted into numbered **tokens**, like numbered magnetic tiles
- The **assembled prompt** is the set of incoming tiles placed on the board for one model call
- The **context window** is the whole board, including space reserved for the answer and any supported reasoning
- Later rounds can add messages and tool results
- **Compaction** replaces some older detail with a shorter summary
- A **new session** starts without the previous conversation history

The aim is not to keep the board empty. It is to give the model the information it needs without burying that information in unrelated material.

## What a token is

A tokenizer splits text into pieces and maps each piece to a number called a **token ID**. The model processes those numbers rather than reading characters in the way a person does.

A piece can be a word, part of a word, punctuation or a special symbol. Product documentation often uses **token** for both the represented piece and the unit being counted.

![One tokenizer turning pieces of text into numeric token IDs](Media/tokenisation-example.svg =720x)

The example shows one tokenizer. Token IDs are not universal. Different models, including models from the same family, can split the same text differently and produce different token counts. Most Copilot users do not need to calculate this manually.

## Prompt, context and context window

These terms are related but not interchangeable:

- **Context** is the information available to the model for the current call
- The **assembled prompt** is the concrete input that packages that context for the call
- The **context window** is the maximum capacity shared by input, generated output and supported reasoning

Copilot reserves room for the model response and can compact older history as a session grows. You normally do not need to manage that reserve yourself.

## Token counts in more detail

| Count | What it represents |
| --- | --- |
| **Input** | Instructions, tool definitions, messages, supplied file content and earlier tool results sent for a model call |
| **Output** | Text and structured tool requests generated by the model |
| **Cached input** | A matching input prefix the provider can reuse from an earlier call |
| **Reasoning** | Internal working used by supported reasoning models, where reported |

Exact prices, cache eligibility and usage displays depend on the model and Copilot client.

## How context grows during a turn

A **turn** runs from your message to Copilot's final response. A **round** is one pass through the model-and-tools loop.

Suppose an agent is fixing a failing checkout test:

1. It finds the repository's checkout test command
2. It runs the focused tests and captures the failure
3. It reads the failing test and relevant implementation
4. It edits the cause and runs the focused test again

![Four rounds carrying earlier context forward, followed by a compacted prompt](Media/context-growth-across-rounds.svg =780x)

In the simplified illustration, each round adds one equal block while carrying earlier blocks forward: `1 + 2 + 3 + 4 = 10` blocks of input processing. Longer turns can therefore grow quickly. Real usage is less tidy because tool output varies and Copilot can use caching, filtering and compaction.

This is a context-growth illustration, not a billing formula. Billing also depends on generated output, model pricing and the Copilot implementation.

## What happens when the window fills

Copilot can compact older conversation history by replacing detail with a shorter summary. This creates space, but a summary might not preserve every exact command, decision or edge case.

VS Code can compact automatically and provides a manual **Compact Conversation** action for supported sessions. Other IDEs expose their own context controls.

Keep information that must survive exactly in a repository or workspace file the harness can read. Chat history should not be the only copy of an important decision.

## Inspect context and usage

Some IDE versions display how much of the context window is used, reserved and free.

![Illustrative context-window indicator showing used, reserved and free capacity](Media/context-indicator.svg =560x)

In current VS Code agent sessions, select the context indicator in Chat to inspect the session and compact it when the control is available. VS Code also provides Agent Debug Logs and Cache Explorer for deeper diagnosis.

[Cache Explorer](https://code.visualstudio.com/docs/agents/agent-troubleshooting/cache-explorer) compares consecutive requests and their matching prompt prefix. Treat it as a cache diagnostic, not as proof of the literal network payload sent to a model provider.

## Common sources of context bloat

- Long instruction files full of rarely relevant workflows
- Several files repeating the same rules
- Attaching a whole folder when a small set of files would do
- Reusing one session for unrelated tasks
- Commands that return large amounts of irrelevant output

Relevant context can improve quality. Irrelevant material can consume capacity, increase processing and make the useful evidence harder to find.
